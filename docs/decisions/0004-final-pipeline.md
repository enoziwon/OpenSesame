# 0004. 제품 파이프라인은 최종본(사전·규칙), 팀 LLM 파이프라인은 1차 비교 대상

- 날짜: 2026-11-15
- 상태: 확정 (11/15 회의)

## 결정

1. **제품은 최종본(`src/final`)으로 한다.** 원재료 사전과 판정 규칙으로 판정하고, 사전·규칙이 모르는 이름만 필요하면 LLM에 묻는다 (`OPENSESAME_FINAL_FALLBACK`).
2. **팀 LLM 파이프라인(`src/pipeline.py` + LLM 분류기)은 1차 비교 대상으로 남긴다.** 같은 정답지(시험 세트 140개)로 1차와 최종을 비교한다.
3. **화면 판정은 4단계를 유지한다**: Confirmed / Likely / Cannot determine / Not detected.
   - Cannot determine과 Not detected는 사용자가 할 일이 달라 합치지 않는다.
4. **LLM 크레딧(402) 문제는 일단 보류한다.** 최종본은 LLM 없이 돈다.

## 배경·경위

- 11/15 회의에서 "사전에 있는 원재료는 사전, 없는 원재료는 LLM·자체 모델(하이브리드)"을 채택했다.
- 정형식 브랜치의 최종본이 이 구조를 이미 구현하고 있었다: 정확 일치 사전 2,790항목 + 키워드 규칙 + 한국 표시란 규칙 + 괄호 속 하위 원료 판단. 테스트 604개 통과 (Python 3.9 / 3.13).
- EXP-003·EXP-005에서 문제가 된 사례(식물성유지(팜유), 혼합조미분말[멸치분말…], 카제인나트륨, 새우맛분말)를 최종본은 정답지 가이드대로 처리한다.
- 같은 입력에 같은 결과, 과금 없음, 제품당 약 1ms.

## 기각한 대안과 이유

- 팀 LLM 파이프라인을 제품으로: 회차마다 답이 흔들리고(17개 중 2개), 크레딧 한도(402)에 걸리며, 정답지 기준과 판정 정의가 다르다.
- 4단계 중 Cannot determine과 Not detected 합치기: Not detected로 합치면 판정 불가가 묻혀 누락과 같은 효과가 나고, Cannot determine으로 합치면 경고 피로가 생긴다.

## 미검증 전제와 남은 위험

- 사전 2,790항목 중 사람이 확인한 것은 일부다 (공식 자료 대조 270, Claude 검토 2,015, 자동 단 1,869 검수 전). 사람 교차 검수 표본이 필요하다.
- 사전 v1.1은 개발 세트 60개를 보며 고쳤다. 최종본의 점수는 **시험 세트 140개로만** 보고한다.
- 1차(LLM)는 크레딧 보류로 시험 세트 결과가 일부뿐일 수 있다. 비교 전에 1차 실행분을 확보해야 한다 (늦어도 11/22 회의 전).
- R2(한국 표시란에 없으면 추정 근거를 지움): 사진 OCR이 표시란을 일부만 읽으면 진짜 알레르기를 지울 수 있고, 정답지도 같은 규칙이라 점수로 드러나지 않는다. 처리 방식 미정.

## merge 때 할 일

- `requirements.txt`, `src/model/llm.py`는 main 쪽(학교 게이트웨이 연결)을 유지한다.
- 제품 서버는 `src/final/app.py`로 하나로 한다. 프론트는 `/analyze`(사진), `/analyze-text`(글자)를 쓴다. 하드코딩한 원재료명은 `/analyze-text`로 바꾼다.
- `feat/text-input`, `feat/eval-runner`는 닫는다 (`/analyze-text`, `tools/run_team.py`가 같은 일을 한다).
- merge 전 수정: 키워드 규칙이 이름 일부만 설명할 때 오타 난 알레르기 이름이 묻히는 문제 (땅공버터 → 우유만, 땅콩 누락).
