# 0003. 단계 사이 데이터 형식과 /analyze 응답

- 날짜: 2026-11-10
- 상태: 제안 (11/9 회의 내용을 코드로 옮김. 팀 확인 후 확정)

## 결정

1. 서버는 사진만 받고, 9개 알레르겐 전부를 판정해 돌려준다. 알레르기 프로필은 서버로 보내지 않고 브라우저에서 대조한다.
2. `allergen`, `verdict` 값은 gold 스키마와 같다 (9개 영문 키, confirmed / inferable / undecidable).
3. 분류기(5단계)의 입출력은 "원재료 이름 목록 → 원재료별 분류"로 고정한다. LLM과 자체 모델이 같은 인터페이스를 쓴다.
4. 제품 단위 합치기는 규칙으로 한다: 알레르겐마다 가장 강한 판정 (confirmed > inferable > undecidable).
5. 화면에서 판정이 없는 항목은 "Not detected"로 쓴다. "Safe"는 쓰지 않는다.

회의 합의안에서 추가한 것 (확인 필요):
- `undecidable_ingredients`: 어느 알레르겐과 관계있는지조차 모르는 원재료 (예: 향료)
- `other_evidence`: 같은 알레르겐의 다른 근거 원재료
- `meta`: 어떤 OCR·분류기·프롬프트 버전으로 나온 결과인지 (평가 재현용)

## 배경·경위

4명이 병렬로 개발하려면 단계 사이 형식이 먼저 고정되어야 한다. 평가 코드가 서버 출력과 gold를 바로 비교하려면 값도 같아야 한다.

## 기각한 대안과 이유

- 사진을 LLM에 통째로 넣고 판정까지 받기: 단계별 오류 분석이 불가능하고, 자체 모델과 같은 조건으로 비교할 수 없다.
- 프로필을 서버로 보내 서버에서 대조: 건강 정보가 서버를 지나간다. 개인정보 원칙 위반.

## 미검증 전제

- 원재료 단위 분류로 충분하다 (원재료 사이 관계를 봐야 하는 경우가 드물다).
- `evidence_ingredient`가 gold의 표기와 글자 단위로 일치하지 않을 수 있다. 평가는 allergen·verdict 기준으로 하고 근거는 부분 일치로 본다.
